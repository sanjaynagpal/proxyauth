§1

The problem

Three specific things about corporate forward proxies that net/http does not, and structurally cannot, handle on its own.

01

No Negotiate/NTLM support

net/http only ever preloads Proxy-Authorization: Basic … from credentials embedded in the proxy URL. It has no concept of a challenge–response scheme — Negotiate and NTLM don't exist to it.

02

The 407 never surfaces

For an HTTPS request the challenge arrives while CONNECT is still being negotiated, so it reaches calling code as an error from RoundTrip — not a *http.Response you can inspect and retry.

03

NTLM remembers the connection

Type 1 → Type 2 → Type 3 must run on one kept-alive TCP connection to the proxy. http.Transport's built-in CONNECT handling tears the connection down the instant it sees anything but 200.

proxyauth exists to own that one connection for exactly as long as the handshake needs it, then quietly hand it back to the standard library.

§2

Architecture

A Transport is really two ordinary *http.Transports wearing one RoundTripper face. It resolves a proxy for each request — Config.Proxy, then Config.ProxyURL, then http.ProxyFromEnvironment — and routes on the result.

No proxy applies: the request goes to direct, dialing straight to the origin exactly as net/http always has. A proxy applies: the request goes to tunneled, whose DialContext is dialTunnel — the only place proxyauth actually intervenes.

Once connect() succeeds, the raw, now-authenticated TCP connection is handed to tunneled exactly as if it had dialed the origin directly — which is why pooled connections stay usable across requests without repeating the handshake.

§3

The handshake

connect() drives every leg of the exchange on the single TCP connection dialTunnel opened, feeding each proxy token into SSPI and writing the result straight back as Proxy-Authorization.

MaxLegs (default 10) bounds how many round trips one handshake may take, and HandshakeTimeout (default 30s) bounds the whole exchange — both exist purely as safety valves against a misbehaving proxy, since a well-behaved NTLM exchange finishes in exactly three legs and Negotiate/Kerberos in one or two.

§4

Kerberos & SPNEGO

Negotiate — the scheme proxyauth prefers — is shorthand for SPNEGO (RFC 4178): an envelope that lets the client and proxy agree on a real mechanism and carries its tokens. When a Kerberos ticket is available, SPNEGO uses it; when it isn't, it quietly falls back to the exact NTLM exchange from Fig. 2, just wrapped in SPNEGO framing instead of sent bare.

Kerberos itself solves one problem: prove your identity once, then use short-lived, service-specific tickets instead of your password everywhere else. Your machine authenticates to a Key Distribution Center (KDC, usually a domain controller) exactly once, at logon, and gets back a Ticket-Granting Ticket — encrypted so only the KDC can read it, valid for hours. Every later request for a specific service exchanges that TGT for a fresh service ticket, named by the service's Service Principal Name (SPN). The service decrypts the ticket with a key only it and the KDC share, and never has to call the KDC to check it.

The SPN is the one piece proxyauth has to get right: spnFor() defaults it to HTTP/<proxy-host> (Config.SPN overrides it). If that doesn't match what's actually registered in Active Directory for the proxy — a load-balanced hostname behind a different SPN, say — the KDC can't issue a matching ticket, and SPNEGO quietly drops to the three-leg NTLM path instead of failing outright. That silent fallback is convenient in production and confusing in debugging: a Negotiate handshake that unexpectedly takes three legs instead of one is usually an SPN mismatch, not a code bug.

§5

Platform split

SSPI is a Windows API, so the actual credential and token machinery lives behind one small interface, swapped in at compile time by build tag.

token(input []byte) is called once per leg: a nil input on the first call produces the opening token (a Kerberos AP-REQ, or an NTLM Type 1 under SPNEGO); every later call feeds in the proxy's continuation token from Proxy-Authenticate and returns the next token to send. negotiateAuth wraps Kerberos-with-NTLM-fallback; ntlmAuth is used when the proxy advertises NTLM only.

§7

Case study: the tunnel that never opened

RFC 7230 §3.3.3 is explicit: a 2xx response to CONNECT has no body — the bytes right after the header block are the tunnel, and a client must not try to read past them as content.

writeConnect didn't know that. It called io.Copy(io.Discard, resp.Body) after every leg, including the final 200. Go's generic response parser only special-cases a zero-length body for HEAD requests — it has no idea this 200 is answering a CONNECT — so a proxy that (correctly, and commonly) omits Content-Length on that final response reads as "body continues until the connection closes." The connection was about to become a live tunnel that never closes. Every such proxy would hang every single request, forever.

How it was found

A local end-to-end test harness plays the server side of NTLM via SSPI against the logged-in Windows account — no domain controller involved (see §8). The very first real handshake hung on the final leg. Reverting the fix and rerunning the new regression test, TestConnectSuccessDoesNotBlockOnBody in proxyauth_test.go, reproduced the identical timeout on demand — confirming the mechanism before the fix was written, not just after.

§8

Testing

Three tiers, each proving something the one before it can't — and all three run on a single Windows machine with nothing external.

TierRunProvesNeeds
Unit tests go test ./... Header parsing, scheme choice, SPN default, keep-alive detection, and the CONNECT-body regression (Fig. 5) — pure logic. Nothing — any OS, <1s.
Build check go build ./... The real SSPI code path in auth_windows.go actually compiles. A Windows toolchain — cross-compiles fine as GOOS=windows from anywhere.
Local NTLM end-to-end go test -run TestNTLMHandshakeLocal The real multi-leg exchange in Fig. 2, driven by genuine SSPI on both ends. A Windows session — no domain controller, via ntlm.AcquireServerCredentials validating locally.

The third tier is the one worth dwelling on: ntlm_local_test.go stands up a fake CONNECT proxy that speaks real server-side NTLM — alexbrainman/sspi/ntlm's NewServerContext — against the same logged-in account running the test, then relays the tunnel to a real httptest.Server. It is the only test here that exercises auth_windows.go for real, and it is what actually caught the bug in §7.
